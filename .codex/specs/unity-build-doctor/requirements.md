## 问题与目标

### 问题陈述

Unity Build 把多个原本独立的翻译单元合并到同一翻译单元。老项目可能依赖匿名命名空间、文件级 `static`、宏状态、include 顺序、条件编译或隐式包含等“每个 `.cpp` 单独编译时成立”的假设；合并后会暴露重定义、名字遮蔽、宏泄漏和类型不完整等问题。qmake 到 CMake 的迁移还可能丢失源文件、宏、包含目录和逐文件选项。仅看一次编译日志，无法可靠地区分这两类问题，也无法知道最小冲突集合和最低风险缓解方式。

### 目标与成功指标

- 普通构建失败时停止 Unity 归因，并把结果标记为迁移/基线问题。
- 普通构建成功、Unity 构建失败时，把失败归属到 target、生成的 Unity 单元及有序源文件集合。
- 对可重放的失败，在不修改用户源码的情况下找到 1-minimal 冲突集合：移除集合中任意一个文件后，相同失败指纹不再复现。
- 将问题归为可解释类别，并为每条结论给出诊断证据、置信度和“为何不是其他类别”的限制说明。
- 输出可复制但默认不应用的 CMake 缓解片段；用户应用后可执行普通/Unity 双模式回归和构建耗时对比。
- 在不少于 8 类合成夹具上，已知问题的 source 定位召回率为 100%，分类正确率至少 90%，且零源码误写。

### 非目标

- 不自动完成任意 qmake 到 CMake 的迁移。
- 不保证自动修复所有 C++ ODR、未定义行为或链接时问题。
- 不在 MVP 中直接改写 `.cpp/.h/CMakeLists.txt`。
- 不用正则表达式替代完整 C++ 语义分析；无证据时输出“未知类别”。
- 不在本 Spec 中实现 Qt GUI、IDE 插件、云服务、Windows/Linux 安装器。

## 角色、术语与范围

### 角色

| 角色 | 目标 | 权限或限制 |
|---|---|---|
| C++/Qt 开发者 | 快速找到导致 Unity 构建失败的文件组合和可行修复 | 决定是否应用生成的建议 |
| 构建/CI 维护者 | 检查哪些 target 可安全启用 Unity，并防止回归 | 可提供配置、target、并发数与探测预算 |

### 术语

| 术语 | 精确定义 |
|---|---|
| 普通构建 | 对同一配置将 Unity Build 关闭后的 configure/build。 |
| Unity 构建 | 对同一配置启用 CMake Unity Build 后的 configure/build。 |
| 失败指纹 | 由编译器、主错误类别、规范化诊断位置/符号和退出状态组成，用于判断探测是否复现同一失败。 |
| 冲突集合 | 在同一 Unity 翻译单元内，能够复现某个失败指纹的有序源文件集合。 |
| 1-minimal | 集合能复现失败，且移除其中任意一个元素后不再复现该失败指纹；不承诺全局最小基数。 |
| 编译探针 | 在独立临时目录生成 Unity driver，并重放目标编译上下文的只编译命令。 |
| 建议工件 | Markdown/JSON 报告和可复制的 CMake 片段；默认不写入目标项目。 |

### 系统边界与依赖

- 范围内：CMake C/C++ target 发现、普通/Unity 构建编排、GCC/Clang/MSVC 风格诊断归一化、失败最小化、规则分类、报告和回归验证。
- 范围外：qmake 语法的完整解释、链接器全平台语义证明、C++ AST 级自动重写、Qt GUI。
- 外部依赖：目标项目使用的 CMake、构建器、编译器；MVP 实现建议只依赖 Python 3 标准库。

## 用户旅程

1. 开发者指定源码目录、独立诊断 build 根目录、配置和可选 target。
2. 工具探测 CMake/生成器/编译器能力并建立会话清单。
3. 工具先运行普通构建；失败则报告基线问题并停止 Unity 最小化。
4. 普通构建成功后运行 Unity 构建，解析失败 Unity 单元及源文件顺序。
5. 工具对每个失败指纹运行有预算、可恢复的编译探针和 delta debugging。
6. 工具结合诊断、源码局部证据、宏/符号特征和顺序实验分类。
7. 工具输出报告、CMake 缓解片段和验证命令；开发者审查并自行应用。
8. 开发者请求验证后，工具重新执行普通/Unity 构建、测试和耗时对比。

## 功能需求

### REQ-001：建立可信构建基线

**用户故事：** 作为开发者，我希望工具先验证非 Unity 构建，从而避免把 qmake→CMake 迁移错误误报为 Unity 冲突。

- 优先级：Must
- 前置条件：给定 CMake 源码目录和独立诊断 build 根目录。
- 结果/副作用：仅在诊断 build 目录和报告目录写入文件。

#### 验收标准

- AC-001.1：当启动诊断时，系统应当记录 CMake、生成器、编译器、配置、target、源码版本标识和命令参数。
- AC-001.2：当普通构建失败时，系统应当标记 `BASELINE_FAILED`、保留原始日志、禁止进入 Unity 冲突最小化，并返回非零退出码。
- AC-001.3：当普通构建成功时，系统应当使用相同源码、配置、target 和除 Unity 开关外相同的用户参数启动 Unity 构建。
- AC-001.4：如果源码目录与指定 build 目录重叠，系统应当拒绝运行并说明安全原因。

### REQ-002：发现失败 Unity 单元与编译上下文

**用户故事：** 作为开发者，我希望看到失败属于哪个 target 和哪些 `.cpp`，从而缩小人工阅读范围。

- 优先级：Must
- 前置条件：REQ-001 普通构建成功、Unity 构建失败。
- 结果/副作用：生成目标与源文件映射，不修改项目。

#### 验收标准

- AC-002.1：当 Unity 编译失败时，系统应当报告配置、target、语言、Unity driver 路径、原始 source 顺序和首个失败指纹。
- AC-002.2：如果 File API、编译数据库或生成 Unity 文件缺失，系统应当指出缺失证据和可执行的重新 configure 方法，不猜测 source 集合。
- AC-002.3：当项目包含多个失败 target 或失败指纹时，系统应当分别建案，且一个案件失败不覆盖其他案件日志。
- AC-002.4：如果问题出现在链接、代码生成或测试阶段而非 Unity 编译步骤，系统应当标记实际阶段，不进入不适用的编译探针。

### REQ-003：最小化可重放冲突

**用户故事：** 作为开发者，我希望得到最小的冲突文件组合，从而不必逐个排除整个 target 的文件。

- 优先级：Must
- 前置条件：已获得 Unity 单元及可重放编译上下文。
- 结果/副作用：只在会话临时目录产生探针源码、对象和日志。

#### 验收标准

- AC-003.1：当完整 source 集合可在探针中复现相同失败指纹时，系统应当使用保持原顺序的 delta debugging 输出 1-minimal 集合及每次探测证据。
- AC-003.2：当失败对 include 顺序敏感时，系统应当保留原顺序，并可通过反序或配对实验标记 `ORDER_SENSITIVE`，不得把无序集合当成等价。
- AC-003.3：如果探针不能复现原始失败，系统应当标记 `NON_REPLAYABLE`，保留原 Unity 单元映射并停止自动最小化。
- AC-003.4：当达到用户定义的次数或时间预算时，系统应当保存会话状态、输出当前最小候选和 `BUDGET_EXHAUSTED`，允许后续恢复。
- AC-003.5：对于只含一个 source 的失败，系统应当标记单文件 Unity/生成上下文问题，不伪造两文件冲突。

### REQ-004：基于证据分类

**用户故事：** 作为开发者，我希望知道“为什么冲突”，从而选择代码修复、分组还是排除。

- 优先级：Must
- 前置条件：至少有原始诊断和 Unity 单元映射。
- 结果/副作用：每个分类包含证据和置信度。

#### 验收标准

- AC-004.1：系统应当至少识别并区分：翻译单元局部名字冲突、匿名命名空间冲突、宏泄漏/条件编译、include 顺序或缺失直接 include、无保护/含定义的头文件、逐文件编译选项差异、Qt/生成源相关、单文件自身错误、未知。
- AC-004.2：当证据不足或多个解释同样成立时，系统应当降低置信度、列出候选解释，不输出“已确认根因”。
- AC-004.3：分类记录应当引用原始诊断、相关 source 行和成功/失败探针，不展示无关源码内容。
- AC-004.4：对“普通构建通过但 Unity 失败”的案件，系统不得仅凭 `redefinition` 文本统一归为 ODR；应结合符号、位置和预处理状态分类。

### REQ-005：生成分级缓解建议

**用户故事：** 作为构建维护者，我希望先使用低风险 CMake 缓解，再决定是否修源码，从而逐步获得编译收益。

- 优先级：Must
- 前置条件：完成定位，分类可为未知。
- 结果/副作用：产生建议工件，不自动应用。

#### 验收标准

- AC-005.1：系统应当按“target 关闭 Unity、source 排除、减小 batch、显式 GROUP、`UNITY_BUILD_UNIQUE_ID` 配合源码改造、宏清理/直接 include/命名修复”的风险和收益说明适用条件。
- AC-005.2：当建议 `SKIP_UNITY_BUILD_INCLUSION` 时，系统应当生成含 target 目录作用域的可复制 CMake 片段，并列出被排除文件和预计损失。
- AC-005.3：当运行 CMake 版本不支持某属性时，系统应当隐藏或标记该建议不可用，并提供兼容替代。
- AC-005.4：如果分类为未知或 non-replayable，系统可以建议最小化后的 source 排除，但不得生成未经证据支持的源码修复。
- AC-005.5：建议必须保留 Unity 开启/关闭由开发者控制，不向项目永久强制 `CMAKE_UNITY_BUILD=ON`。

### REQ-006：报告、隐私与恢复

**用户故事：** 作为开发者，我希望报告可读、可供 CI 处理且可恢复，从而能在大项目中持续排查。

- 优先级：Must
- 前置条件：诊断会话已创建。
- 结果/副作用：写入用户指定报告目录。

#### 验收标准

- AC-006.1：每次运行应当输出 schema 版本化 JSON 和 Markdown 摘要，二者引用同一案件 ID、失败指纹和证据文件。
- AC-006.2：默认报告应当记录规范化相对路径和必要源码片段，不收集源码全文、环境变量值或凭据。
- AC-006.3：相同输入和会话清单恢复时，系统应当复用已完成探针；源码、编译命令或工具链指纹变化时，应当使相关缓存失效。
- AC-006.4：用户中断进程时，系统应当尽力原子保存会话状态，并保证目标源码树未被修改。

### REQ-007：验证缓解效果

**用户故事：** 作为构建维护者，我希望同时验证正确性和编译收益，从而避免用“能编译”交换回归或负优化。

- 优先级：Should
- 前置条件：开发者已在自己的工作树审查并应用建议。
- 结果/副作用：产生验证报告，不回滚或修改用户变更。

#### 验收标准

- AC-007.1：当请求验证时，系统应当执行普通和 Unity 两种构建以及用户指定测试命令，并分别报告退出状态。
- AC-007.2：当任一正确性验证失败时，系统应当把建议标记为未验证，不宣称修复完成。
- AC-007.3：当请求性能对比时，系统应当记录至少 3 次 clean build 的中位耗时、机器/并发/配置条件，并报告相对变化；不足 3 次时仅展示原始数据。

| ID | 类别 | 可测约束 | 测量方式 |
|---|---|---|---|
| NFR-001 | 安全 | 默认运行不得改变源码树中任何文件的内容、权限或时间戳；所有临时写入位于显式 build/report 根目录。 | 运行前后树哈希与文件元数据快照测试 |

| NFR-003 | 兼容性 | 对 CMake/编译器能力做运行时探测；未知或不支持时失败可解释，不静默套用属性。 | 多版本夹具与能力矩阵测试 |

| NFR-005 | 性能 | 用户可设置最大探针次数和墙钟时间；达到预算后 5 秒内产出部分报告。 | 预算耗尽集成测试 |

## 边界、错误与状态转换

| 场景 | 预期行为 | 关联 ID |
|---|---|---|
| 普通构建失败 | 归为基线/迁移问题，停止 Unity 诊断 | REQ-001 |
| Unity 构建通过 | 报告该配置未复现，不做冲突分类 | REQ-001, REQ-006 |
| Unity 编译失败但探针不复现 | 保留原映射，标记 non-replayable | REQ-002, REQ-003 |
| 同一批次多个独立错误 | 按失败指纹分别最小化，已知一个案件不遮蔽其他案件 | REQ-002, REQ-003 |
| 编译器崩溃/超时/内存不足 | 独立归为基础设施失败，不当作源码重定义 | REQ-003, REQ-006 |
| 用户 Ctrl-C | 保存状态、终止子进程、保持源码树不变 | REQ-006 |
| 源码在恢复前发生变化 | 使关联探针失效并重新运行 | REQ-006 |

## 约束、假设与风险

### 已确认约束

- 设计必须支持 CMake 项目，且不能假定 qmake 工程仍可执行（FACT-001、FACT-003）。
- MVP 核心不依赖 Qt（FACT-003、UNK-001）。
- 项目仓库无业务代码可修改，此轮只产出规格（FACT-002）。

### 待验证假设

- ASM-001：MVP 采用 Python 3 标准库 CLI；若用户要求单文件原生二进制或 Qt GUI，需要重新打开设计阶段。
- ASM-002：第一阶段支持 C/C++ 编译失败；CUDA/Objective-C/Objective-C++ 和链接时 ODR 作为后续扩展。
- ASM-003：目标项目允许创建独立的诊断 build tree，并能导出编译数据库或读取 CMake File API。

### 风险

- RISK-001：编译命令重放与真实构建可能因生成文件、响应文件、编译器 launcher 或环境差异而不一致；必须显式允许 `NON_REPLAYABLE`。
- RISK-002：宏和 include 顺序问题可能依赖三个以上文件，不能只做两两组合。
- RISK-003：自动排除文件很容易让构建通过但损失大部分加速收益，因此报告需要估算排除比例并做性能验证。
- RISK-004：C++ 诊断格式跨编译器变化，规则必须容忍未知，不能以误分类换覆盖率。

## 需求分析记录

| ID | 类型 | 涉及需求 | 发现 | 决议/接受风险 |
|---|---|---|---|---|
| ANA-001 | 歧义 | REQ-001, REQ-004 | “很多重定义”可能是 CMake 迁移错误，也可能是 Unity 翻译单元语义变化。 | 强制普通构建先行，普通构建失败时禁止 Unity 归因。 |
| ANA-002 | 隐含假设 | REQ-003 | 冲突不一定是两个文件，也可能是有序的三文件宏链。 | 使用保持顺序的 delta debugging，目标为 1-minimal 而非 pair。 |
| ANA-003 | 安全缺口 | REQ-005, REQ-006 | 自动改源码/CMake 可能破坏用户未提交改动。 | MVP 只输出建议工件，不自动应用。 |
| ANA-004 | 可测试性 | REQ-004 | “找到根因”不可直接量化。 | 用分类、置信度、证据链和固定夹具的准确率衡量。 |
| ANA-005 | 冲突约束 | REQ-005, REQ-007 | 排除越多越容易通过，但 Unity 收益越低。 | 输出排除比例，要求双模式正确性和可选性能验证。 |
| ANA-006 | 恢复缺口 | REQ-003, REQ-006 | 大项目探针可能耗时，单次全跑不可靠。 | 增加预算、原子状态与恢复缓存。 |
| ANA-007 | 平台未知 | 全部 | Windows/Linux、Qt 版本和发布方式未知。 | 核心接口跨平台设计，只把 macOS arm64 写成当前可验证环境。 |
